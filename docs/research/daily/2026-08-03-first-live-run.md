每日情报纵向闭环已经通过两次真实网络运行。首次运行证明多信源降级下仍可产出榜单，同时暴露出搜索语法、输出路径和方向覆盖问题；修复后的第二次运行保持 `60 → 20 → 20` 的处理规模，并让五个方向全部达到至少 3 个项目。

首次运行有三个关键发现：

2. 根脚本通过嵌套 pnpm 启动 worker，pnpm 改变了进程工作目录，因此显式相对 `--output` 被解析到 `workers/daily/` 下。

OpenSSF 对这批 20 个新近候选均没有结果。这表示覆盖缺失，不表示这些仓库存在安全问题。

## 稳定化修改

- 把五个 GitHub Search 查询改为真实 API 验证可用的文本 OR 查询；最小验证请求返回 HTTP 200。
- 根命令改为直接运行 `tsx workers/daily/src/cli.ts`，保留用户发起命令时的仓库根目录。
- 每个方向配置 3 个高质量候选仓库，在外部发现源降级时提供可采实体。
- 配置候选与 GitHub 归入同一 independence group，且 `rank`、速度、讨论等指标全部为空；它不会制造独立印证或趋势加分。
- 候选容量先保留每个方向的最低数量，再按全局发现质量补满。
- 某信源返回的候选全部超过新鲜度阈值时，健康状态改为 `degraded`。
- 为上述边界增加配置、发现、健康度和根命令回归测试。

## 验收判断

通过：

- 实时模式、日期、时区和生成时间均显式记录；
- 多发现源并行运行，单源故障不会吞掉整份日报；
- 每个方向有最低覆盖，配置兜底不参与虚假趋势加分；
- 所有补全项目都有 GitHub REST 证据；
- 综合榜不含归档仓库；
- 缺失许可证进入风险扣分，缺失 Scorecard 只降低证据完整性；
- JSON、Markdown 和 manifest 均可解析并通过统一数据契约。

仍需继续观测：

- GitHub Trending HTML 端点在当前网络环境不稳定；
- HubLens 当前数据更新时间不足以作为当日趋势证据；
- OpenSSF 不是全仓库覆盖，不能把缺失误读为安全通过；
- GitHub Events 只提供有限的近期公开事件，是活跃度代理而不是完整贡献历史；
- 隐藏宝石榜当前为空，说明证据门槛有效，但也需要后续接入包管理器采用数据提升识别能力。

下一工程阶段应让网站只读取 `DailyReport` 契约，先完成首页综合榜、方向榜、项目详情和信源健康页；随后再做 Obsidian 同步，最后开放个性化 Agent 接入。
