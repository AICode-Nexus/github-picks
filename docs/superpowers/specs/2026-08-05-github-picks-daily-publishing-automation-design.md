# GitHub Picks 每日三次自动发布设计

**日期：** 2026-08-05

**状态：** 已确认设计，待实施

**调度：** Asia/Shanghai 每日 10:00、14:00、20:00

## 目标

在保留现有真实信源、GitHub 事实补全和本机 Ollama AI 推荐理由强校验的前提下，每天自动运行三次实时日报流水线。每次运行只有在数据、AI、工程门禁和静态网站构建全部通过后，才把当天日报提交到 `master` 并触发 GitHub Pages 发布。

自动化还应立即补发 2026-08-05 日报，并让后续每次运行都留下可审计的 Git 提交、Pages 运行记录和任务内结果摘要。

## 已选方案

使用附着于当前 Codex 任务的单个本地 heartbeat 自动化，复用本机已经可用的：

- GitHub CLI 登录和短时读取的 GitHub Token；
- Ollama `qwen3-vl:8b` 模型；
- Node.js 24.15.x、pnpm 11.18.0 和仓库现有依赖；
- 当前仓库的 live 流水线与 GitHub Pages 工作流。

不采用 GitHub 托管 Runner，因为仓库当前没有远端模型 Secret，托管 Runner 也不能访问本机 Ollama。暂不安装 GitHub 自托管 Runner，因为 Codex heartbeat 已能满足本地定时执行和结果回报，额外 Runner 不会消除“本机必须在线”的约束。

## 运行隔离

自动化使用固定的独立 Git worktree 和 `codex/` 前缀分支，不直接在用户正在使用的 `master` 工作区生成文件。每次运行开始时必须：

1. 确认 worktree 没有本任务范围外的未提交改动；
2. 获取 `origin/master`，且只允许快进同步；
3. 确认 GitHub CLI 已认证、Ollama 服务可访问且目标模型存在；
4. 确认当前北京时间对应的日报日期。

任何前置条件失败都应停止本次运行，不采集、不提交、不清理未知文件，并在当前任务中报告精确原因。

## 数据与发布流程

```text
定时触发
  -> 环境与 Git 前置检查
  -> 代码门禁
  -> live 采集到隔离输出目录
  -> 确定性日报发布门禁
  -> 更新 artifacts/daily/YYYY-MM-DD 三份正式产物
  -> 网站静态构建
  -> 仅提交三份日报产物
  -> 推送到 master
  -> 等待并核验 Pages
  -> 回报结果
```

实时采集必须设置：

- `GITHUB_TOKEN`：仅从 `gh auth token` 注入当前进程，不落盘；
- `GITHUB_PICKS_AI_PROVIDER=ollama`；
- `GITHUB_PICKS_AI_MODEL=qwen3-vl:8b`；
- `GITHUB_PICKS_AI_REQUIRED=true`。

原始网络响应继续写入被 Git 忽略的 `artifacts/raw/`。可提交边界保持为当天目录中的 `report.json`、`report.md` 和 `manifest.json`，网站和其他消费者仍只读取 `DailyReport` 契约。

## 确定性发布门禁

新增一个可测试的发布校验入口，至少验证：

1. 日期等于本次北京时间日报日期，且 `mode` 为 `live`；
2. 至少两个真实网络发现源为 `healthy`；
3. GitHub REST 事实补全没有整体离线；
4. 五个方向榜都有项目，公开综合榜不含归档仓库；
5. 每个公开项目都有 GitHub REST 证据；
6. 缺失事实保留在 `sourceHealth` 或 `missingFields` 中；
7. `ai-analysis` 为 `healthy`，每个公开项目的 AI 生成状态均为 `verified`；
8. `report.json`、`report.md` 和 `manifest.json` 三份产物一致且可解析。

发布前还必须运行仓库完整 `pnpm check`；正式产物进入日报目录后必须运行网站生产构建。任一门禁失败时，不提交或推送新日报。

## Git 与并发策略

- 同一天三次采集覆盖同一日报目录，网站按最新 `generatedAt` 展示；Git 历史保存三次观测差异。
- 每次提交只包含当天三份日报文件，提交信息包含日期和北京时间档位。
- 推送使用快进语义；若运行期间远端 `master` 前进，停止并报告，不强推、不自动改写他人提交。
- heartbeat 使用一条包含三个小时的日程规则，避免创建三个互相竞争的自动任务。
- 若产物与当前提交完全一致，则作为无变更运行报告，不创建空提交。

## 失败与恢复

- 信源部分降级可以保留在日报中，但必须满足发布门禁；不得伪造、回填或沿用旧事实作为本次新采集。
- AI 模型不可用、任一公开项目 AI 理由未通过事实边界校验、测试失败或网站构建失败时，本次不发布。
- 流水线先在隔离目录生成候选产物；失败时不覆盖已发布日报。
- Pages 失败不会删除上一版部署；自动化报告对应提交和 Actions URL，下一档运行重新尝试正常链路。
- 自动化不执行强推、历史改写、整仓清理或未知文件删除。

## 验证与可观测性

实施阶段需要覆盖：

- 发布门禁的通过、错误日期、replay、信源不足、方向缺失和 AI 降级测试；
- live 流水线的现有测试、类型检查与格式检查；
- 网站对新日报的生产构建；
- 自动化创建后读取其状态，确认 `ACTIVE` 和三个北京时间档位；
- 首次 2026-08-05 发布后核对本地提交、远端 `master` 哈希、Pages 运行结论和页面展示日期。

每次自动运行在当前任务中报告：日期、档位、发现/补全/发布数量、降级信源、AI 校验数量、提交号、推送结果、Pages 结果。失败报告必须明确指出停在哪一道门禁。

## 运行约束

本方案依赖本机在三个时段保持开机、Codex 可执行自动任务、Ollama 服务可用且网络可访问 GitHub 与各发现源。机器休眠或离线时不会补造错过的历史观测；下一次正常触发只发布当时的真实快照。

## 非目标

- 不改变现有评分权重、榜单算法或 AI Prompt；
- 不把 AI 引入评分或名次计算；
- 不提交 `artifacts/raw/`、凭据或本机配置；
- 不新增邮件、飞书或其他外部推送渠道；
- 不把 replay 产物发布到网站。
